================================================================================
                         WHY THE 2x ERROR APPEARS
================================================================================

When RTL doesn't convert back to fixed-point at pixel values, the next
iteration of the pipeline receives a position that's already been processed
differently.

Example sequence:

Python:
  Step 0: x = 0xA0000 (160.0 px)  → Move by 1.0 px → x = 0xA1000 (161.0 px)
  Step 1: x = 0xA1000 (161.0 px)  → Move by 1.0 px → x = 0xA2000 (162.0 px)
  Step 2: x = 0xA2000 (162.0 px)  → Move by 1.0 px → x = 0xA3000 (163.0 px)
  Total: 3 pixels in 3 steps ✓

RTL:
  Step 0: x = 0xA0000 (160.0 px)  → Move by 1.0 px → x = 0xA0400 (160.0 + FP error)
  Step 1: x = 0xA0400 (confused)  → Move by 1.0 px → x = 0xA0800 (160.0 + 2×FP error)
  Step 2: x = 0xA0800 (confused)  → Move by 1.0 px → x = 0xA0C00 (160.0 + 3×FP error)
  Total: ~2.0 pixels per step (ERROR!)

The FP coordinates keep accumulating because they're not being "reset" to pixel
values at each step like Python does.

================================================================================
                    THE FIX: MATCH PYTHON'S 3-STAGE PROCESS
================================================================================

Current RTL (BUGGY):
  UPDATE_POS: x_new = wrap_fp(x_reg + dx)  ← Stays in FP

Fixed RTL (CORRECT):
  UPDATE_POS:
    1. wrapped_fp = wrap_at_bit_boundary(x_reg + dx)
    2. pixel_x = to_pixel(wrapped_fp)
    3. pixel_x_wrapped = wrap_pixel(pixel_x)
    4. x_new = to_fixed_point(pixel_x_wrapped)

This ensures positions are properly "reset" to pixel values at each step,
matching Python's semantics exactly.
